# Jenkinslog MVP — Final Implementation Specification

## 1. Goal

Implement a small, portable Python tool named `jenkinslog.py` that reads Jenkins Pipeline console logs of arbitrary size and converts them into a sequence of semantically meaningful, size-bounded chunks.

The primary use case is to ship the script directly inside an LLM skill:

```text
skill/
├── SKILL.md
└── scripts/
    └── jenkinslog.py
```

An LLM/agent must be able to invoke it through a regular shell command without compilation, package installation, or a separate service.

Primary processing pipeline:

```text
Jenkins consoleText
        ↓
    Normalizer
        ↓
Jenkins structure parser
        ↓
Workload-aware parsing
        ↓
 Semantic chunker
        ↓
      JSONL
        ↓
       LLM
```

`jenkinslog` MUST NOT perform failure diagnosis or invoke an LLM.

Its responsibility is to safely split large Jenkins logs into LLM-sized chunks while preserving execution structure, context, and source provenance.

---

# 2. Core Principles

Implementation priorities, in order:

1. Never lose log content.
2. Process logs as a stream.
3. Preserve Jenkins execution context.
4. Preserve workload context.
5. Respect the configured chunk size.
6. Preserve accurate source provenance.
7. Produce deterministic output.
8. Remain a simple and portable script.
9. Do not attempt root-cause analysis.

If the parser does not understand a line, it MUST preserve the line rather than discard it.


Example usage:

# 6. JSONL Output

Each stdout line represents one chunk.

Example:

```json
{"id":"chunk-0001","sequence":1,"stage":"Checkout","step":"sh","command":"git fetch ...","workload":"shell","tokens":6211,"line_start":1,"line_end":731,"continuation":false,"content":"..."}
{"id":"chunk-0002","sequence":2,"stage":"Build","step":"sh","command":"docker build -t app:123 .","workload":"docker","docker_operation":"build","tokens":11731,"line_start":732,"line_end":1921,"continuation":false,"content":"..."}
{"id":"chunk-0003","sequence":3,"stage":"Build","step":"sh","command":"docker build -t app:123 .","workload":"docker","docker_operation":"build","tokens":10981,"line_start":1922,"line_end":2811,"continuation":true,"content":"..."}
```

JSONL is required to support streaming consumers.

# 7. Python API

Provide a simple importable API.

Example:

```python
from jenkinslog import JenkinsLogParser

parser = JenkinsLogParser(
    max_tokens=12_000,
    overlap_lines=30,
)

for chunk in parser.parse_file("console.log"):
    print(chunk.context.stage, chunk.tokens)
```

Also support streams:

```python
with open(
    "console.log",
    "r",
    encoding="utf-8",
    errors="replace",
) as f:
    for chunk in parser.parse(f):
        ...
```

`parse()` MUST NOT require loading the entire input into memory.

# 8. Data Model

Prefer simple `dataclass` structures.

Example:

```python
@dataclass
class SourcePosition:
    line_start: int
    line_end: int
    byte_start: int | None = None
    byte_end: int | None = None


@dataclass
class Block:
    type: str
    name: str | None = None


@dataclass
class JenkinsContext:
    stage: str | None = None
    step: str | None = None
    command: str | None = None
    workload: str | None = None

    branch: tuple[str, ...] = ()
    stack: tuple[Block, ...] = ()


@dataclass
class Chunk:
    id: str
    sequence: int

    context: JenkinsContext
    content: str

    tokens: int
    source: SourcePosition

    continuation: bool = False
    previous_tail: str = ""

    docker_operation: str | None = None
```

The exact structure may be adjusted if this significantly simplifies the implementation.

Do not create a complex Jenkins object model.

# 12. Jenkins Execution Stack

Maintain a best-effort execution stack.

Example:

```text
stage(Build)
  └─ parallel
      └─ branch(Linux)
          └─ container(node)
              └─ sh
```

Do not attempt to reconstruct a complete Jenkins Pipeline AST.

Console logs may be:

- incomplete;
- truncated;
- malformed;
- produced by third-party plugins;
- mixed with ordinary stdout;
- unexpectedly nested.

When structure cannot be reliably reconstructed, prefer:

```text
preserve content
+
degrade metadata
```

over failing parsing.

# 13. Command Detection

For Jenkins `sh`, detect shell commands on a best-effort basis.

Example:

```text
[Pipeline] sh
+ npm test
```

should result in approximately:

```text
stage = Test
step = sh
command = npm test
workload = npm
```

Command detection MUST be conservative.

Do not implement a full shell parser.

If a command cannot be reliably determined:

```text
command = null
```

is preferable to an incorrect guess.

The original output MUST always be preserved.

# 14. Multiline Shell Commands

Support shell continuation.

Example:

```text

    --build-arg COMMIT=abc123 \
    -t registry.example/app:123 \

```

Continuation lines MUST NOT be lost.

A complete shell AST is not required.

Preserving the raw command is more important than perfectly interpreting it.

# 17. Docker BuildKit

BuildKit output MUST influence semantic chunking.

Example:

```text
#1 [internal] load build definition from Dockerfile
#1 transferring dockerfile: 1.2kB done

#2 [internal] load metadata for docker.io/library/golang:1.24

#5 [2/8] RUN npm ci
#5 12.31 downloading ...
#5 ERROR: process "/bin/sh -c npm ci" did not complete successfully
```

A BuildKit operation such as:

```text
#5 [2/8] RUN npm ci
...
#5 ERROR: ...
```

should preferably remain in one chunk if it fits within the configured token budget.

BuildKit operation boundaries are MEDIUM semantic boundaries.

Do NOT:

- reconstruct the Dockerfile;
- construct a BuildKit dependency graph;
- analyze image layers;
- diagnose Docker failures.

# 22. Token Counter

The parser MUST NOT depend on Qwen or any other specific model.

```python
        ...
```

Provide:

```python
class ApproxTokenCounter:
```

# 23. Chunking Strategy

Chunking MUST consider Jenkins and workload semantics.

Use three classes of boundaries.

## Strong boundaries

Preferred locations for closing a chunk:

```text
end of Jenkins stage
end of parallel branch
end of major Pipeline block
```

## Medium boundaries

Preferred locations when approaching the token budget:

```text
new Jenkins sh step
new significant Jenkins step
new Docker operation
BuildKit operation boundary
new npm command
new Go command
new Python command
```

## Weak boundaries

Ordinary output lines.

Use weak boundaries only when the current semantic unit itself exceeds the configured token budget.

---

# 24. Protected Semantic Units

When they fit within the token budget, avoid splitting:

```text
BuildKit failed operation
npm test failure block
Go test failure block
Go panic + stacktrace
Python traceback
pytest failure block
```

This does NOT mean the parser should understand or diagnose the failure.

It only means related output should preferably remain together.

If a protected unit itself exceeds the budget, it may be split.

---

# 25. Chunk Budget

Example:

```text
max_tokens = 12000
```

Normal chunks should remain approximately within this limit.

A small controlled deviation is acceptable when required to preserve a small semantic unit.

Large deviations are not acceptable.

If a command generates:

```text
60K tokens
```

it MUST be split.

---

# 26. Oversized Commands

Example:

```text
Stage: Build
Step: sh
Command: docker build -t app:123 .
Workload: docker

60K tokens
```

Expected result:

```text
chunk-0012
stage=Build
step=sh
command=docker build ...
workload=docker
continuation=false

chunk-0013
stage=Build
step=sh
command=docker build ...
workload=docker
continuation=true

chunk-0014
...
```

All continuation chunks MUST preserve the original execution context.

For Docker BuildKit, prefer splitting between BuildKit operations.

The same mechanism applies to oversized npm, Go and Python output.

---

# 27. Contextual Overlap

Do not use arbitrary token overlap as the primary mechanism.

Support:

```text
--overlap-lines 30
```

For continuation chunks, expose:

```python
previous_tail: str
```

containing the last N lines of the previous chunk.

IMPORTANT:

`previous_tail` MUST NOT be included inside `content`.

Therefore:

```text
content
    = unique source material

previous_tail
    = duplicated context
```

This distinction is required to preserve exact source ownership.

# 29. Provenance

Every chunk MUST contain:

```text
line_start
line_end
```

If this can be implemented without significantly complicating streaming processing, also expose:

```text
byte_start
byte_end
```

Line provenance is mandatory.

Byte provenance is optional for the MVP.

A downstream analyzer must be able to report:

```text
Evidence:
chunk-0014
lines 12871-12893
```

without guessing source positions.

---

# 30. Information Preservation Invariant

This is a critical requirement.

After normalization:

> Every source log line MUST belong to exactly one `Chunk.content`.

No source line may silently disappear.

`previous_tail` does not count as ownership because it contains duplicated context.

A reconstruction test MUST exist:

```text
input
  ↓
normalization
  ↓
parser / chunker
  ↓
ordered Chunk.content
  ↓
concatenate
  ↓
normalized input
```

The reconstructed output MUST match the normalized source according to documented normalization rules.

This is one of the primary acceptance tests.

# 31. Streaming Requirements

The normal parsing path MUST NOT do:

```python

```

for the entire input.

Memory usage should primarily depend on:

```text

+

+
```

The implementation should conceptually be capable of processing:

```text
1 GB console.log
```

without allocating approximately 1 GB of RAM.

# 39. Acceptance Criteria

The MVP is complete when all of the following are true:

1. `jenkinslog.py` runs on Python 3.11+ without `pip install`.
2. It accepts Jenkins console logs from a file.
3. It accepts Jenkins console logs through stdin.
4. Input is processed as a stream.
5. Output is JSONL.
6. Output consists of ordered chunks.
7. Chunks approximately respect `max_tokens`.
8. Jenkins stages are recognized.
9. Jenkins `sh` steps are recognized.
10. Execution nesting is preserved on a best-effort basis.
11. Parallel Pipeline output does not cause parser failure.
12. Shell commands are detected on a best-effort basis.
13. Multiline shell commands are preserved.
14. Docker operations are recognized.
15. BuildKit boundaries influence semantic chunking.
16. npm workloads are recognized.
17. Go workloads are recognized.
18. Python/pytest workloads are recognized.
19. Relevant small failure blocks are kept together where possible.
20. Oversized Docker/npm/Go/Python output is correctly split.
21. Continuation chunks preserve Jenkins and workload context.
22. ANSI formatting is normalized.
23. Line provenance is correct.
24. `previous_tail` does not violate source ownership.
25. Malformed/truncated input does not silently lose remaining content.
26. Reconstruction tests pass.
27. All tests run using:

```bash
python3 -m unittest
```

28. The core implementation has no third-party dependencies.
29. The core implementation contains no LLM logic.
30. Maven, Gradle and Windows support are absent.

# 40. Definition of Done

The final result should be a small, boring, deterministic Python script:

```text
Jenkins console log
        ↓
  jenkinslog.py
        ↓
 semantic chunks
        ↓
      JSONL
```

that can be placed directly inside an LLM skill:

```text
jenkins-debug/
├── SKILL.md
└── scripts/
    └── jenkinslog.py
```

and executed without additional deployment:

```bash
python3 scripts/jenkinslog.py console.log
```

The tool does not need to understand **why the Jenkins build failed**.

It must ensure that a downstream LLM can incrementally investigate the entire build log without loading the full log into its context, without losing source lines, and while retaining enough Jenkins, Docker, npm, Go, and Python execution context for later diagnosis.

This is the version I’d use as the implementation spec for the coding agent.
